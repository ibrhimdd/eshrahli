# اشرحلي | Eshrahli AI ✏️

منصة تعليمية بمدرس ذكاء اصطناعي يحوّل الدروس والكتب إلى شروحات وخرائط ذهنية تفاعلية، ويتيح للطالب أن يسأل ويتدرّب ويتابع فهمه.

> **مهم عند استكمال المشروع:** هذا الملف هو سجل القرارات والخطة المتفق عليها حتى 25 نوفمبر 2026. البنود الموجودة تحت «الخطة» هي مقترحات وقرارات تصميمية لم تُنفّذ بعد ما لم يُذكر صراحة أنها موجودة في النسخة الحالية. لا تفترض أن الميزات المخطط لها تعمل بالفعل.

## 1. الرؤية والهدف

تطوير النسخة الحالية من أداة ترسم خريطة ذهنية إلى مدرس ذكي متكامل يستطيع:

- شرح موضوع يكتبه الطالب بلغة بسيطة، مع أمثلة وتوضيحات وأسئلة متابعة.
- تحويل عنوان عام أو نص أو درس أو فصل من كتاب إلى خريطة ذهنية واضحة.
- استقبال ملفات PDF النصية واستخراج محتواها وتنظيمه وتخزينه.
- الإجابة عن أسئلة الطالب بالاعتماد على المحتوى الذي رفعه، مع ذكر الفصل/الصفحة متى توفرت البيانات.
- توليد اختبارات وأسئلة تدريبية وتصحيحها وشرح الإجابات.
- دعم محادثة صوتية مباشرة في مرحلة مستقلة.
- حفظ المستندات والخرائط والمحادثات وتقدم الطالب.

الفكرة الأساسية: **مدرس واحد، مع إمكانية اختيار نموذج الذكاء الاصطناعي المناسب لكل مهمة، دون ربط الواجهة بمزود واحد.**

## 2. الوضع الحالي للمستودع

المستودع الحالي نموذج أولي (Prototype / MVP)، وليس منصة مكتملة أو جاهزة للإنتاج.

### الملفات والبنية الحالية

```

├── frontend/
│   └── index.html
└── backend/
    ├── server.js
    ├── routes/
    │   └── mindmap.js
    ├── package.json
    └── .env.example
```

### ما هو موجود بالفعل

- واجهة عربية RTL مبنية بـ HTML وCSS وJavaScript خالص.
- سبورة تعتمد على SVG لرسم الخريطة الذهنية تدريجيًا، مع حركة وزوم وتمرير.
- أربعة موضوعات محلية جاهزة: المرايا في الفيزياء، الدورة الدموية، الثورة الفرنسية، والتمثيل الضوئي.
- موضوعات أخرى يمكن إرسالها إلى API الباك إند.
- باك إند Node.js وExpress، ومسار `POST /api/mindmap` ومسار فحص صحة `GET /api/health`.
- تكامل أولي سابق مع Anthropic عند توفر المفتاح، مع fallback عام عند غياب المفتاح أو فشل الطلب.

### قيود النسخة الحالية

- المحادثة ليست مدرسًا متكاملًا، وأسئلة المتابعة لا تنفذ حوارًا حقيقيًا مع نموذج الذكاء الاصطناعي.
- لا يوجد نظام حسابات أو قاعدة بيانات أو حفظ للمستندات والخرائط والمحادثات.
- أزرار رفع الصور والصوت في الواجهة الحالية ليست تكاملات مكتملة.
- قائمة الموضوعات المحلية محدودة، وfallback الحالي لا يُعد شرحًا موثوقًا لأي موضوع.
- عنوان API الافتراضي في الواجهة هو localhost ويجب تغييره عند النشر.
- لا توجد بعد معالجة كتب PDF أو بحث دلالي أو اختبارات تعليمية متكاملة.

## 3. القرارات المعمارية المتفق عليها

### 3.1 مدير موحّد لمزودي ونماذج الذكاء الاصطناعي

استخدام طبقة مستقلة في الباك إند، مقترح تسميتها `AI Provider Manager`، حتى يستطيع التطبيق التعامل مع أكثر من مزود دون تغيير واجهة المستخدم أو منطق السبورة.

- **OpenRouter:** بوابة اختيارية موحدة للوصول إلى نماذج نصية متعددة. نعرض للمستخدم النماذج المتاحة فعليًا، ومعلومات المزود والسعر/حالة المجانية والقدرات عندما توفرها الخدمة.
- **Gemini:** يمكن استخدامه مباشرة أو عبر OpenRouter بحسب توفر النموذج والقدرات والسعر. لا نفترض أن كل نموذج يدعم PDF أو الصور أو JSON المنظم.
- **اختيار النموذج حسب المهمة:** يمكن أن يختار المستخدم نموذجًا للشرح، وآخر للخرائط، وآخر للاختبارات. ويمكن توفير اختيار تلقائي اختياري.
- **النماذج المجانية:** لا نعرض النموذج على أنه مجاني إلا بعد قراءة بيانات التسعير/الإتاحة الحالية من المصدر. حدود المجاني والحصص ومعدل الطلبات قابلة للتغيير.
- **لا تحويل تلقائي إلى نموذج مدفوع:** إذا فشل نموذج مجاني، نعرض الخطأ أو نقترح بديلًا مجانيًا. لا نرسل الطلب إلى نموذج مدفوع دون موافقة واضحة.
- **توحيد المخرجات:** كل موفر يعيد صيغة داخلية موحدة. مخرجات الخرائط والاختبارات يجب التحقق منها (schema validation) قبل عرضها.

يجب أن تكون مفاتيح API في متغيرات بيئة الباك إند أو مخزن أسرار آمن، وليس في JavaScript بالمتصفح أو مستودع GitHub. لا يُطلب من الطالب وضع مفاتيح المزودين داخل الواجهة العامة.

### 3.2 الصوت منفصل عن محرك النصوص والخرائط

الخطة هي استخدام Gemini للصوت/المحادثة المباشرة عبر تكامل صوتي مستقل، حتى لا يقيد اختيار نموذج النصوص محرك الصوت.

- اسم «Gemini Flash Audio 3.5» الذي ذُكر في النقاش لم يتم التحقق من مطابقته لاسم نموذج رسمي؛ يجب مراجعة أسماء النماذج المتاحة في وثائق Google وقت التنفيذ.
- نختار نموذج Live/Native Audio متاحًا ومدعومًا في الحساب والمنطقة وقت التنفيذ.
- لا نخلط بين نموذج الصوت المباشر ونموذج توليد الخرائط النصية.
- يجب مراعاة أذونات الميكروفون، وإدارة الجلسة، وحدود الاستخدام، وإظهار حالة الاتصال والأخطاء.

## 4. إدخال الكتب والملفات — النطاق الأول: PDF النصّي فقط

اتفقنا أن نؤجل حاليًا ملفات PDF المصوّرة (الصفحات الممسوحة ضوئيًا) لتقليل التعقيد والتكلفة. في المرحلة الأولى نقبل PDF حقيقيًا يحتوي على نص قابل للاستخراج والتحديد والنسخ.

### مسار رفع ومعالجة PDF

1. يستقبل التطبيق ملف PDF ويتحقق من نوعه وحجمه وعدد صفحاته.
2. يستخرج النص باستخدام PDF.js أو مكتبة مناسبة على الخادم. يجب أن تكون المعالجة موثوقة حتى لو كان النص في بعض الصفحات قليلًا.
3. يفحص الصفحات المستخرجة: إذا كان النص فارغًا أو أقل من حد مناسب، يرفض الملف باعتباره مصوّرًا/غير مدعوم حاليًا، ويعرض رسالة واضحة تطلب PDF نصّيًا.
4. ينظف النص من التكرار والهوامش غير المفيدة مع الحفاظ على المحتوى العلمي.
5. يكتشف العناوين والفصول والصفحات، ثم يقسم النص إلى مقاطع صغيرة متماسكة (Chunks) حسب الفقرات والعناوين، لا حسب عدد أحرف ثابت فقط.
6. يخزن المستند ومقاطع النص وبيانات المصدر في Firestore.
7. ينشئ Embedding لكل مقطع مرة واحدة، ويحفظ المتجه مع المقطع.
8. يعرض للمستخدم حالة المعالجة والتقدم، ثم يتيح إنشاء خرائط أو سؤال المدرس عن المستند.

**رسالة الرفض المقترحة للملف المصوّر:**
«هذا الملف يبدو أنه PDF مصوّر أو لا يحتوي على نص قابل للاستخراج. حاليًا نقبل ملفات PDF النصية التي يمكن تحديد النص فيها ونسخه. دعم الملفات المصوّرة سيضاف في مرحلة لاحقة.»

لا نعتمد على امتداد الملف وحده؛ يجب فحص النص المستخرج فعليًا. كما يجب عدم اعتبار PDF الذي يحتوي على صور قليلة ورسوم توضيحية ملفًا مصوّرًا بالكامل إذا كان نصه قابلًا للاستخراج.

### المرحلة اللاحقة: PDF المصوّر وOCR

بعد استقرار مسار PDF النصّي، يمكن إضافة OCR كخدمة منفصلة. الخيارات التي ندرسها وقتها تشمل OCR عبر مزود خارجي أو قدرات فهم المستندات/الصور في نموذج يدعمها. لا نضيف OCR الآن ولا نرسل كل ملف إلى خدمتين بلا حاجة.

## 5. التخزين وقاعدة المعرفة — الاستفادة من مشروع Ibrahim-Alkhooly

المستخدم لديه مشروع سابق:
https://github.com/ibrhimdd/Ibrahim-Alkhooly

تمت مراجعة أجزاء من ذلك المشروع، ووجدنا فيه أفكارًا قابلة لإعادة الاستخدام:

- تخزين معلومات في Firebase Firestore.
- إضافة بيانات يدويًا ورفع ملفات، مع استخراج نص PDF باستخدام PDF.js.
- تقسيم النص إلى أجزاء.
- توليد Embeddings باستخدام Gemini، وكان من أسماء النماذج الموجودة في المشروع `models/gemini-embedding-2-preview`.
- البحث عن المعلومات واسترجاعها قبل إرسال السياق إلى نموذج المحادثة.
- تكامل محادثة نصية وصوتية/مباشرة في المشروع السابق.

هذه **مرجعية تصميمية** وليست ضمانًا أن كل اعتماد أو اسم نموذج ما زال متاحًا أو مجانيًا. قبل إعادة استخدام أي كود أو موديل، افحص الملفات الحالية والتوثيق والتوفر والأسعار. لا تنسخ أسرار API أو مفاتيح Firebase أو بيانات خاصة من المشروع القديم.

### هيكل Firestore المقترح

الأسماء التالية اقتراح مبدئي قابل للتعديل:

- `users`: حسابات الطلاب والإعدادات.
- `documents`: بيانات الكتب والدروس المرفوعة، بصمة الملف، عدد الصفحات، حالة المعالجة، والمالك.
- `document_chunks`: مقاطع النص، رقم الصفحة، الفصل/العنوان، وترتيب المقطع، وEmbedding.
- `mindmaps`: الخرائط الناتجة، مصدرها، النموذج المستخدم، وبيانات JSON.
- `chat_sessions`: جلسات المحادثة ورسائلها ومراجع المستندات المستخدمة.
- `quizzes`: الاختبارات والأسئلة والإجابات والتقييم.
- `processing_jobs`: حالة معالجة المستندات، الأخطاء، وعدد المقاطع المنجزة.

يجب وضع قواعد Firestore بحيث لا يستطيع المستخدم قراءة أو تعديل مستندات مستخدم آخر. صلاحيات الإدارة والكتابة الحساسة تكون من خلال الباك إند أو قواعد موثقة وآمنة.

### منع إعادة المعالجة وتقليل التكلفة

- حساب SHA-256 للملف أو للمحتوى المستخرج لاكتشاف الملفات المكررة.
- إذا كانت بصمة الملف موجودة لنفس المستخدم ولم يتغير المحتوى، نعيد استخدام النصوص والـ Embeddings بدل توليدها مجددًا.
- إنشاء Embedding مرة واحدة لكل Chunk، وإعادة إنشائه فقط إذا تغير النص أو نموذج التضمين/إصداره.
- تخزين إصدار نموذج التضمين المستخدم حتى لا نقارن متجهات من نماذج/مساحات مختلفة دون قصد.
- لا نرسل الكتاب كاملًا إلى نموذج التوليد إذا كان المطلوب فصلًا واحدًا أو سؤالًا محددًا.

## 6. البحث الدلالي وRAG

نستخدم أسلوب Retrieval-Augmented Generation (RAG):

1. يأخذ النظام سؤال الطالب.
2. ينشئ Embedding للسؤال باستخدام نفس نموذج التضمين المستخدم للمقاطع.
3. يبحث في المقاطع ذات الصلة باستخدام بحث متجهي في Firestore إذا كانت إعدادات المشروع والفهرس تدعم ذلك.
4. نضيف بحثًا نصيًا/كلمات مفتاحية أو آلية هجينة لتحسين نتائج الأسماء والمصطلحات الدقيقة.
5. نرتب النتائج ونختار أفضل المقاطع ذات الصلة فقط.
6. نرسل السؤال والمقاطع المحددة إلى نموذج الشرح المختار.
7. نطلب إجابة مستندة إلى المصادر، مع ذكر الصفحات/العناوين، والتصريح إذا كانت المعلومة غير موجودة في الملفات.

يجب التحقق من إمكانات Firestore Vector Search وحدودها ومتطلبات الفهارس والتكلفة وقت التنفيذ. لا نعتمد على تنزيل كل قاعدة البيانات إلى المتصفح وحساب التشابه محليًا عند نمو البيانات.

## 7. إنشاء الخرائط الذهنية

الخريطة ليست تلخيصًا نصيًا فقط؛ المطلوب بناء شجرة معرفية:

- عقدة رئيسية تمثل الموضوع.
- فروع رئيسية للأفكار والمحاور.
- فروع فرعية للمفاهيم والتفاصيل والأمثلة.
- علاقات واضحة وعدم تكرار الأفكار.
- الحفاظ على الحقائق كما وردت في الكتاب عندما يكون المصدر كتابًا.
- التمييز بين معلومات المصدر والمعلومات العامة الإضافية.

### أوضاع الإدخال

- **عنوان فقط:** إنشاء خريطة من المعرفة العامة للنموذج، مع توضيح أنها ليست مقتبسة من كتاب محدد.
- **نص أو درس:** استخراج الأفكار من النص المقدم.
- **فصل من كتاب:** استرجاع مقاطع الفصل ذات الصلة وبناء خريطة مستندة إليها.
- **كتاب كامل:** معالجة الفصول على مراحل، وإنشاء خرائط فرعية ثم خريطة عامة تربط المحاور. لا نحاول إرسال كتاب طويل كاملًا في طلب واحد.

### عقد البيانات (اقتراح)

يجب الاتفاق على JSON schema ثابت بين الباك إند والواجهة، يتضمن مثلًا:
- `title`
- `branches[]`
- `label`
- `highlight`
- `children[]`
- `sourcePages[]` أو مراجع المصدر عند توفرها.

نحافظ على التوافق مع الشكل الذي تستخدمه السبورة الحالية أو ننفذ محولًا (adapter) بين الصيغة الموحدة والصيغة القديمة. لا نعرض JSON غير صالح على السبورة؛ نتحقق منه ونطلب إصلاحه أو نعرض خطأ مفهومًا.

## 8. وحدات المدرس الذكي المستهدفة

1. **الشرح التفاعلي:** شرح مبسط، أمثلة، إعادة شرح، وأسئلة متابعة حقيقية.
2. **الخرائط الذهنية:** إنشاء الخريطة من عنوان أو نص أو فصل/كتاب.
3. **اسأل كتابك:** إجابات مبنية على المقاطع المخزنة مع مرجع الصفحات.
4. **الاختبارات:** أسئلة اختيار من متعدد وصح/خطأ وأسئلة قصيرة، مع تصحيح وتفسير.
5. **التدريب على نقاط الضعف:** إعادة تدريب الطالب على المفاهيم التي أخطأ فيها.
6. **الصوت المباشر:** محادثة صوتية عبر Gemini Live/Native Audio بعد التحقق من اسم الموديل المتاح.
7. **حساب الطالب والتقدم:** حفظ المحادثات والخرائط والاختبارات والتقدم في مراحل لاحقة.

## 9. خطة التطوير المرحلية

### المرحلة 0 — تثبيت الأساس
- مراجعة المستودع والنسخة الحالية قبل كل تعديل.
- الحفاظ على السبورة SVG والمواضيع المحلية الحالية.
- توثيق متغيرات البيئة وعدم وضع أي مفاتيح سرية في Git.
- تحديد شكل JSON موحد للخرائط ورسائل الأخطاء.

### المرحلة 1 — طبقة مزودي الذكاء الاصطناعي
- إنشاء واجهة موحدة لمزودي النماذج في الباك إند.
- إضافة OpenRouter كمزود للنصوص، مع إمكانية Gemini المباشر.
- جلب قائمة النماذج والأسعار والقدرات من API عند الإمكان، وعدم تثبيت قائمة قديمة في الواجهة.
- تمكين اختيار نموذج لكل مهمة: شرح، خريطة، اختبار.
- دعم وضع مجاني فقط، ومنع التحويل إلى نموذج مدفوع دون موافقة.
- التحقق من JSON ومخرجات النماذج وتسجيل أخطاء الطلبات دون تسجيل المفاتيح.

### المرحلة 2 — مدرس نصي حقيقي
- تحويل أسئلة المتابعة إلى محادثة حقيقية في الباك إند.
- إضافة سياق المحادثة مع حدود واضحة لطول السياق.
- إضافة أوضاع «اشرح ببساطة»، «أعطني مثالًا»، «اختبرني»، و«أنشئ خريطة».
- إزالة fallback المضلل أو توضيح أن النموذج غير متاح بدل تقديم خريطة عامة على أنها صحيحة.

### المرحلة 3 — PDF النصّي والتخزين
- إضافة رفع PDF والتحقق من أنه نصّي.
- استخراج النص وتنظيفه وتقسيمه حسب الفصول والفقرات.
- إعداد Firebase Authentication وFirestore وقواعد الأمان.
- تخزين المستندات والمقاطع وحالة المعالجة.
- إضافة منع التكرار ببصمة الملف.
- واجهة تعرض تقدم الرفع والمعالجة والأخطاء.

### المرحلة 4 — Embeddings والبحث الدلالي
- اختيار نموذج Embedding متاح ومناسب للعربية بعد اختبار الجودة والتكلفة.
- توليد متجهات المقاطع وتخزينها.
- إعداد Vector Index والبحث المتجهي في Firestore بعد التحقق من متطلبات الخطة والمنطقة.
- إضافة البحث الهجين وترتيب النتائج.

## المرحلة التالية المنفذة — Firebase Auth وPDF النصّي

### ما تم إضافته فعليًا

- Firebase Admin SDK في `backend/services/firebase-admin.js` لتهيئة Firestore والتحقق من ID Tokens.

- رفض الملفات التي لا تحتوي على نص قابل للاستخراج برسالة توضح أنها قد تكون PDF مصوّرة.

- حفظ بيانات المستند في `documents` ومقاطع النص في `documents/{documentId}/chunks`.
- منع تكرار معالجة نفس الملف لنفس المستخدم عبر SHA-256.
- عرض قائمة الملفات للمستخدم وحذف ملفه ومقاطع النص التابعة له.

- الواجهة تبدأ فهرسة الملف تلقائيًا بعد استخراج النص وتعرض عدد المقاطع المتبقية.
- endpoint `POST /api/documents/:id/ask` لتوليد متجه السؤال، واسترجاع أقرب المقاطع من Firestore، ثم إرسال السياق فقط إلى مدرس OpenRouter.
- إجابات الكتاب تطلب الاستناد للمقاطع المسترجعة وذكر أرقام الصفحات، وتعيد مصادر الصفحات المستخدمة.

### إعداد Gemini

أضف إلى متغيرات بيئة الباك إند:

```env
GEMINI_API_KEY=your_server_side_key
GEMINI_EMBEDDING_MODEL=gemini-embedding-2
EMBEDDING_TIMEOUT_MS=30000
```

مفتاح Gemini يبقى على السيرفر فقط. نموذج `gemini-embedding-2` يعرض حاليًا طبقة مجانية للمدخلات النصية في جدول أسعار Gemini، لكن الحدود والتوفر قد تتغير؛ راجع الأسعار والحصص قبل الاستخدام الفعلي.

### إنشاء Vector Index في Firestore

بعد إنشاء Firestore، يلزم إنشاء فهرس متجهي لمجموعة المقاطع `chunks` بالحقل `embedding` وبأبعاد 768. باستخدام Google Cloud CLI:

```bash
gcloud firestore indexes composite create \
  --collection-group=chunks \
  --query-scope=COLLECTION \
  --field-config field-path=embedding,vector-config='{"dimension":"768","flat":"{}"}' \
  --database="(default)"
```

انتظر حتى يصبح الفهرس جاهزًا في Google Cloud Console. بدون الفهرس، سيستطيع النظام رفع النص وتخزينه، لكن البحث الدلالي لن يعمل بعد.

### واجهات RAG الجديدة

| Method | Endpoint | الوظيفة |
|---|---|---|
| POST | `/api/documents/:id/index` | إنشاء Embeddings لمقاطع الملف على دفعات |
| POST | `/api/documents/:id/ask` | سؤال الملف واسترجاع مقاطع مناسبة مع صفحاتها |

كل هذه المسارات تتطلب Firebase ID Token. طلب السؤال يحتاج أيضًا `OPENROUTER_API_KEY` ومفتاح `GEMINI_API_KEY`.

### حدود التنفيذ الحالي

- البحث الدلالي يعمل داخل ملف واحد في كل طلب، ويتحقق من ملكية الملف قبل البحث.
- البحث المتجهي يحتاج إلى Vector Index يدوي في مشروع Firestore.
- لم يتم بعد إضافة بحث كلمات مفتاحية/Hybrid Search أو إعادة ترتيب النتائج.
- لم يتم بعد ربط إجابات «اسأل كتابك» بجلسات محفوظة، ولا إنشاء الخرائط الذهنية من محتوى الكتاب.
- لم يتم اختبار استدعاءات Gemini وFirestore على مشروع Firebase حقيقي؛ يلزم ضبط مفاتيح المشروع وإنشاء الفهرس ثم اختبار ملف فعلي.
- رفع الملفات مفهرس نصيًا فقط؛ لا يوجد OCR في هذه المرحلة.

### مصادر تقنية تم التحقق منها

- Gemini Embeddings: https://ai.google.dev/gemini-api/docs/embeddings
- Gemini API Pricing: https://ai.google.dev/gemini-api/docs/pricing/
- Firestore Vector Search: https://firebase.google.com/docs/firestore/vector-search


### تنبيه خصوصية مهم

في إعداد Gemini API المجاني الحالي، تنص صفحة الأسعار على أن المدخلات قد تُستخدم لتحسين منتجات Google؛ لذلك لا ترفع مستندات سرية أو بيانات شخصية/حساسة باستخدام مفتاح مجاني قبل مراجعة شروط المزود وسياسة البيانات. يتم إرسال نص المقاطع إلى Gemini لإنشاء Embeddings، ثم تُرسل المقاطع المسترجعة إلى نموذج الشرح عبر OpenRouter. راجع شروط وسياسات كل مزود، واختر إعدادًا تجاريًا مناسبًا للبيانات الحساسة عند الحاجة.
